# Форматы файлов юнитов Disciples III (geo2011)

Реверс-инжиниринг формата по образцам репозитория и строкам/таблицам из
`geo2011.dle` (3ds Max DLL импорта/экспорта, исходники плагина бинари .g/.a
писались закрыто — экспортный writer в `export.dll`, которого в репо нет).
Все утверждения ниже проверены на образцах round-trip'ом (байт-в-байт, см.
«Верификация»); поля, значение которых не удалось вывести из данных,
помечены как непрозрачные и при экспорте сохраняются как в оригинале.

Один юнит (персонаж) = набор файлов с общим «корнем» имени в одной папке:

| файл      | назначение |
|-----------|-----------|
| `*.g`     | геометрия: вершины, веса, лица, скелет (bind), атрибуты |
| `*.a`     | анимация (все клипы в одной последовательности кадров) |
| `*.ac`    | текстовый конфиг анимации: клипы, события, ссылки |
| `*.scene` | текстовое описание сцены/объектов (gobj'ы, атрибуты) |
| `*.t`     | атлас текстур: DXT1/3/5 + mipmap-цепочки |

Пример: `character_empire_inquisitor.g/.a/.ac/.scene/.t`.

## Соглашения о данных

* Все бинарные файлы — little-endian, плотная упаковка (без выравнивания,
  кроме явно указанных отступов).
* Строки: `uint32 длина + байты` (без терминирующего нуля).
* Имена файлов/текст в `.ac`/`.scene`: как правило ASCII/latin-1;
  пути могут содержать обратные слеши (`.\file.t`) — при разборе
  использовать НЕ `shlex` (он интерпретирует `\`), а собственный
  токенайзер.

### Система координат

Пространство файла (и вершин, и translations матриц костей) — правое,
«Y вверх, X вбок, Z вперёд» (запечённый поворот из 3ds Max):

```
высота (голова y≈1.66)  → +Y
боковое (левая рука)    → +X
глубина                 → +Z
```

Соответствие Blender (Z up):

```
bl.x =  f.x
bl.y = -f.z
bl.z =  f.y
```

### Матрицы костей (в .g)

Строки 16 float: `M = [r0; r1; r2; T]`, конвенция строковых векторов
(`v' = v @ M`). В `.g` хранится **обратная bind-матрица** `G = inv(W)`:
skinning: `v_bone = v_world @ G`. Проверено на Hips: строки поворота
(0,1,0),(1,0,0),(0,0,-1) (перестановка осей Max-кости),
`row3 = -T·Rᵀ = (-1.0148, 0, 0)` — точно совпадает. Bind-мир кости =
`inv(G)`; translation обратных матриц лежит в том же Y-up пространстве,
что и вершины (Head T=(0,1.656,-0.017), LeftFoot (0.2,0.118,0.039)).

## .g — геометрия

### Заголовок / meta (на секцию-материал)

Файл начинается с одного «главного» блока meta, затем идут секции mesh.
Структура (для `character_empire_inquisitor.g`, все offset'ы точные):

```
@0    u32 = 3            (версия/магия)
@4    u32 aux            (непрозрачно, 0 у образца)
@8    u32 = 1
@12   27× float32        (непрозрачный массив параметров)
...   string material    (имя материала)
...   string object name
@345  первая секция mesh
```

Точное смещение каждой секции хранится в поле-таблице; парсер в `g3.py`
вычисляет их последовательным обходом (размер секции априори неизвестен).

### Секция mesh

```
u_prefix  (непрозрачные байты, сохраняются как есть)
14× float32:
  [0..2]   pos3        позиция пивота/корня (у тела =Translation Reference-кости
                       ≈ (0.0004, 0.9053, -0.0025); у оружия — высота руки)
  [3..5]   rot3         всегда 0 (кватернион-поворот секции не используется)
  [6..8]   bbox_max
  [9..11]  bbox_min
  [12]     radius       радиус сферы отсечения (culling); у образца это
                        max-компонентная норма bbox — при пересчёте возможны
                        расхождения ~1e-4 (незначительно), поэтому при
                        неизменной геометрии экспорт сохраняет оригинал
  [13]     = -1.0
u32 nattr + nattr × (string key, string value)   — атрибуты материала:
   material0_diffuse ".\имя.t", name, weights_on_vertex, bones_num,
   material0_triangles_num, vertexs_weights_num, twosided, ...
u32 nv  число вершин
vert×  (см. ниже)
u32 nf  число треугольников
face×  3× u32 индексы вершин
u32 nbone + nbone × (string имя кости, 16× float32 G)  — таблица костей
```

Запись вершины (wov = `weights_on_vertex`, у тела =4, у оружия =1):

```
u32 color              (RGBA байты: r,g,b,a; типично 0x0BC5D864)
3× float32 co          позиция
3× float32 no          нормаль
u32 = 0xFFFFFFFF       паддинг (всегда у образцов)
2× float32 uv          v сверху вниз (directx-стиль!) — в Blender v' = 1 - v
wov>1:  (wov-1)× f32 веса; wov× u8 индексы костей в таблице bones
        (веса хранятся без последнего — нормализуются на движке;
         нулевые слоты сохраняются при экспорте дословно)
```

Секция оружия (`weapon_empire_inquisitor`, nv=537, wov=1) не имеет весов:
жёстко привязана к первой (единственной) кости таблицы `Weapon1`, вершины
лежат в локальном пространстве этой кости (нож вдоль +X, bind-матрица
Weapons1 = unit, T=0).

## .a — анимация

```
u32 payload_size (= размер всего файла - 8)
u32 = 0
27× float32 заголовка (fps и т.п.; у образца fps=15)
u32 frames        (301 у образца)
u32 ntrack        (27)
track×:
  u32 id
  u32 parent_id   (0xffffffff = корень; в .ac ссылки по имени)
  string name     (имя кости)
  string parent   ("Scene Root" у корня)
  float32 scale   (= 0.01 — перевод cm → m)
  frames × (7× float32: qx qy qz qw px py pz)
```

**Семантика ключей** (проверено данными idle/attack/death):

* `q` — **полная локальная ротация** кости в её собственных осях, т.е.
  уже «с учётом» перестановки осей из bind (у Hips key0 ≈172° вокруг оси
  (1,1,0) — это swap-оси Max + наклон idle; у Reference — yaw ≈ -16°).
* `p` — **дельта позиции относительно translation bind-локала**
  (локальный offset кости из .g), в сантиметрах (×scale).
* Цепочка поз (строковые матрицы): `Lf = [R(q); t_Lb + p·0.01]`,
  `Wf[b] = Lf[b] @ Wf[parent]`, корень (`Reference`) умножается на
  тождественную.  `t_Lb` — translation bind-локала,
  `Lb[b] = Wb[b] @ inv(Wb[parent])`, `Wb = inv(G)` из .g.

Таким образом `.a` переопределяет и ротацию, и (дельтой) позицию всех
костей целиком; bind-матрицы `.g` задают базу и skinning-матрицы G.
Композиция совпадает с цепочкой `bone.matrix_local @ matrix_basis`
Blender 1-в-1 после глобального преобразования осей, т.к.
`matrix_local == C(Lb)` (см. формулы в `__init__.py`).

Клип-нарезка (Idle/Attack/…) задаётся не в .a, а в .ac (кадры 0-based,
в Blender кадры = f+1).  Все 301 кадр анимируются целиком (движок сам
выбирает окно клипа).

## .t — текстуры

```
u32 magic/format? — 27 байт заголовок:
  u32 unk0, u32 width, u32 height, u32 format_id, u32 mips, ...
  format_id: 6 = DXT1, 7 = DXT3, 8 = DXT5, 0/2 = A8R8G8B8/X8R8G8B8
mips × (width>>i × height>>i, от большого к 8×8), плотно:
  DXT1 блоки 8 байт (16×16), DXT3 16 байт (4 байта alpha + 2×DXT1-color),
  DXT5 16 байт (alpha 8 байт + 2 блока)
```

Сумма размеров mips + 27 = точный размер файла (проверено на 2048²:
2 796 219 байт).  Atlas у инквизитора один на тело+оружие
(`material0_diffuse = ".\character_empire_inquisitor.t"` у обеих секций).

## .ac — конфиг анимации (текст)

```
child
{
  anim_state "Idle" { frame0 1 frame1 134 fps 15 }
  ...
  link Idle -> Attack ...
  event ...
  gaestate ...
  meshfile "...";
}
```

Разбор — простой скобочный токенайзер (см. `scene.py`): строки `'{ ' в
одиночку приклеиваются к предыдущей, `'}'` закрывает блок.  Фреймы:
Idle 1–134, Attack 134–188, Damage 188–234, Death 234–281, Run 286–299
(границы перекрываются: конец одного = начало другого; интерпретация
`frame0/frame1` = «кадры клипа», 0-based в .a — при импорте +1).
Экспорт `.ac` не переписывает (файл копируется как есть), т.к. правки
клипов аддоном не поддерживаются.

## .scene — сцена (текст)

```
scene { child gobj { objname "empire_inquisitor" meshfile "x.g" meshindex 0
  coords 0.000414 0.905286 -0.002483  attr "..." "..." ...
  child bone { name "Hips" } ... } }
```

* `coords` gobj'а совпадают с `pos3` (floats[0..2]) соответствующей секции
  .g (для тела) и с pos3 оружия (0.915, 0.0012, 0) — синхронизируются
  экспортёром только счётчики (`material0_triangles_num`,
  `vertexs_weights_num`, `bones_num`, `weights_on_vertex`); coords —
  из оригинального файла (правка пивота не поддерживается).
* `child bone` списки → имена костей; `.scene` сохраняет
  `bones_file "…​.a"` — связь с анимацией.

## Верификация

* `g3.read_g → g3.write_g` — байт-идентично (271 893 B); то же через
  весь экспортный путь (`prepare_mesh_section` + пересчёт атрибутов) —
  идентично.
* `a3.read_a → a3.write_a` — байт-идентично (228 508 B), и отдельно —
  полный цикл «ключ → Blender basis → ключ» с декомпозицией:
  0 изменённых ключей, байт-идентичный файл.
* Физическая проверка модели поз: z(Head) в idle 1.647…1.669 м (bind
  1.656), Hips 1.015 стаб., ноги 0.12…0.66 (run-замахи), голова на
  Death опускается до 0.89 — всё согласуется с ожиданиями.
* `t3.read_t → write_t_dxt1` — точный размер/заголовок (перекодирование
  DXT1 — свой encoder, байт-совпадения с оригиналом не гарантируются).

## Ограничения аддона (v0.1)

* Экспорт опирается на оригинальные файлы-шаблоны (пути пишутся в JSON
  `armature['d3unit']`); создать юнит «с нуля» нельзя — можно править
  геометрию/веса/анимацию импортированного.
* Правка rest-pose поддерживается частично: `.g` G-матрицы пересчитываются
  из `matrix_local`, `.a` использует `matrix_local` как базу — при
  рассогласовании с движком возможна деформация (движок берёт G из .g,
  а t_Lb — из .g же, см. формулы; экспорт согласован с импортом).
* `.t`: при экспорте с опцией текстур перепаковывается DXT1 первого mip'а
  и mip-цепочка (медленно: 2048² ≈ 13 c); DXT3/5 перекодирование —
  best-effort (альфа-нибблы).
* Непрозрачные поля (aux, u_prefix, 27 f32 meta, rot3, color'а вершин)
  сохраняются/воспроизводятся как в оригинале; новые вершины получают
  color из соседних, UV вне 0..1 недопустимы движком (не проверяется).
* Кватернионы при записи нормализуются к w ≥ 0 (тот же поворот;
  сравнение с оригиналом учитывает знак).

## Файлы аддона (blender/io_scene_d3unit/)

| модуль    | роль |
|-----------|------|
| `g3.py`   | парсер/писатель `.g` (byte-exact) |
| `a3.py`   | парсер/писатель `.a` (byte-exact) |
| `t3.py`   | `.t`: чтение, декод DXT1/3/5→RGBA, запись DXT1 |
| `scene.py`| токенайзер/парсер `.scene` и `.ac` |
| `unit.py` | сборка «юнита», 4×4-математика, пересчёт секций |
| `__init__.py` | импорт/экспорт Blender, armature, меши, материалы, экшены |
