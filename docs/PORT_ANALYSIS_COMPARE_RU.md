# Архив `Port.rar`: разбор и сверка с `d3tool`

Дата: 7 ноября 2026 г. Источник: коммит `7f237a1` в `main`
(`Port.rar`, 732 410 байт). Архив распакован в `/tmp/Port` — 206 файлов,
1.8 МБ, из них 110 файлов кода/документации и ~96 `__pycache__`.

Документ отвечает на два вопроса: **что нового в архиве** и **где это
сходится или расходится с тем, что уже реализовано и проверено в `d3tool`
и Blender-аддоне**. Всё, что взято в код, помечено ссылкой на файл.

---

## 1. Что это за проект

`Port` — не аддон и не конвертер моделей. Это протокол переноса моделей
**Heroes VII → Disciples III**: семь комплектов `h7*` (`h7battlebear`,
`h7blackbear`, `h7justiciar`, `h7runepatriarch`, `h7shieldguard`,
`h7defender`, `h7priestess`) внутри `NewUnit.vdpack`, их `.g/.a/.ac/.scene/.t/.char`
и длинная серия runtime-экспериментов в игре.

| Файл | Что это |
|---|---|
| `PORTING_ANALYSIS_RU.md` (1063 строки) | основная аналитика: `.vdpack`, `.a`, `.g`, `.t`, bind-матрицы, runtime-опыты, выводы |
| `D3MODEL_README_RU.md` (482 строки) | описание CLI `d3model` и статус экспериментов |
| `d3model.py` (249 строк) | standalone: `inspect`/`extract`/`validate`/`manifest`/`pack` для `.vdpack` |
| `_work_blender/*.py` (~100 файлов) | зонды форматов: `d3g_container.py`, `d3a_container.py`, `d3g_bind.py`, `geo2011_a.py`, `psa_to_d3a.py`, dozens of `build_*_test.py` |
| `_work_blender/dependencies/psk_psa_py` | колесо `io_scene_psk_psa` для чтения H7 PSK/PSA |

Главное отличие от нашего репозитория: у Port **нет** доступа к `dis3tool`
как к библиотеке, поэтому они шли двумя путями — (а) собственная
реконструкция форматов по байтам и (б) **дизассемблирование официального
плагина `geo2011.dle`**. Второй путь дал то, чего у нас в документации не
было: точную грамматику `.a` из самого экспортёра Max.

## 2. `.a` — грамматика официального writer'а

Ключевой фрагмент `PORTING_ANALYSIS_RU.md`:

> Официальный geo2011 writer (VA `0x100077C0`, `0x10007610`, `0x10020D20`)
> опроверг 36-byte header/quaternion-prefix и position shift1.

То есть их **первая** реконструкция (`36-байтный заголовок`, `16-байтные
quaternion-префиксы` у каждой кости, сдвиг позиций на кадр) была неверной;
корректная грамматика — в `_work_blender/geo2011_a.py`:

```text
header  <5I     = (magic 9, len-8, track_count, frame_count, fps)      20 байт
repeat per track:
    <3If        = (len(name)+1, len(parent)+1, samples, scale)         16 байт
    name + NUL                       -- len считает NUL
    parent + NUL                     -- len == 0 => БАЙТОВ НЕТ ВООБЩЕ
    samples * <7f                    -- quaternion xyzw, position xyz   28 байт
```

Проверка `to_bytes() == data` в `parse()` — то есть ссылочный парсер сам
требует побайтовой воспроизводимости.

**Сверка с нами.** `d3tool/anim.py` реализует ровно эту грамматику:
20-байтный заголовок, `<IIIf`-преамбула на запись, имена, кадры `<7f`
(quat + trans — порядок совпадает), длина `len-8` без trailing-блока.
Корпусные `.a` (153 файла, 6764 записи) сходятся с грамматикой на 100%:

| Проверка | Результат по корпусу |
|---|---|
| `len(name)+1 == name_len` во всех записях | 6764/6764 |
| `len(parent)+1 == parent_len` | 6764/6764 |
| `parent_len == 0` (пустой родитель) | 0 случаев — в D3 корневой родитель всегда `Scene Root` |
| 5-е слово заголовка | `15` (139 файлов), `30` (12), `16` (2) |
| `scale` записи | 15 разных значений, мода `0.01` (5524 записи из 6764) |

Что из этого **взято в код** в этом раунде:

1. `parse_anim` читает имена **по длине из преамбулы**, а не поиском NUL
   (`anim._read_lp_name`). Это единственный способ пережить `parent_len == 0`
   и вообще то, что делает официальный writer; при несоответствии длины
   остаётся откат на старый NUL-скан, так что ручные правки файлов не ломаются.
2. `write_anim` больше не пишет `\x00` для пустого родителя — ровно как
   официальный writer (0 байт).
3. `build_anim(..., fps=15, scale=0.02)` — раньше оба значения были зашиты.
   Теперь это параметры: `fps` пишется в 5-е слово заголовка (geo2011
   называет его fps), `scale` — в преамбулу каждой записи.
   Значения по умолчанию сохранены, чтобы не сдвинуть побайтовый паритет
   обратного экспорта (донор всё равно подставляет свои преамбулы).

Проверено тестами: `test_anim_track_without_parent_uses_zero_length`,
`test_anim_build_takes_fps_and_track_scale`.

**Где Port нам не указ.** Их «1-based inclusive» диапазоны `.ac` — это
наблюдение по семи перенесённым комплектам, а не правило движка: в игровом
корпусе 568 из 591 состояния начинаются с кадра 1, но **23 начинаются с 0**.
`d3tool` хранит `frame0/frame1` дословно и не «исправляет» их — это верно.

## 3. `.g` — контейнер и вершины

`_work_blender/d3g_container.py` — независимый парсер, читающий `.g` без
игрового кода. Его утверждения:

```text
[u32 3][u32 len] ...            -- один или несколько node-заголовков
[u32 1][u32 4][u32 mesh_count]  -- заголовок набора мешей
per mesh:
    [u32 2] ... 84-байтный блок  -- = 28 (заголовок) + 56 (scene-матрица)
    [u32 n_props] (key,value)*   -- блок атрибутов, строки с длиной
    vertices * stride
    indices * u32
    bones: (u32 len, name+NUL, 16 float матрицы)
    [опционально tangent-поток: 8 + vertex_count*24 байт]
```

Вершинные записи по Port:

* `N = 0` или `1` — `stride 40`;
* `N = 3` — 40 + 2 явных веса + 3 индекса;
* `N = 4` — 40 + 3 явных веса + 4 индекса;
* rigid `N = 1` требует ровно одной кости (проверено на трёх моделях).

Это **полностью совпадает** с нашей формулой
`40 + 4*(w-1) + w` (`gfile.vertex_stride`) и с тем, что мы уже описали
в `docs/FORMATS.md`. Независимое подтверждение полезно: наш вывод был
сделан по 160 `.g` корпуса, их — по H7-файлам, полученным сторонним
экспортёром, и формулы совпали.

**Новое для нас — tangent-поток.** У нас в корпусе (160 `.g`) атрибута
`tangent` нет вообще, но Max-плагин пишет его, когда включены тангенты:
`8 + vertex_count*24` байт сразу после таблицы костей. Раньше такой файл
разобрался бы до первой части с `tangent`, а дальше парсер «съехал» бы на
потоке и потерял остальные части. Добавлено в `gfile._parse_compound_parts`
(поток уходит в `part_tail`, `_part_block` пишет его обратно в том же
порядке), тест — `test_compound_part_keeps_tangent_stream`.

**Bind-матрицы.** `_work_blender/d3g_bind.py` выводит их из PSK так:

```python
inverse = np.linalg.inv(axis @ global_h7 @ axis.T)   # axis = (x,z,y)
encoded = struct.pack('<16f', *inverse.T.reshape(-1))
```

То есть в 64-байтном блоке лежит **inverse-global bind, записанная
по столбцам** (`transpose` строкового представления). Наша
`frame.cmaj16()` читает этот блок как column-major — то есть как
`inverse_global` в терминах glTF (`inverseBindMatrices`), и в обратном
экспорте мы пишем ровно эти 16 float'ов. Согласование полное, менять
ничего не нужно; но теперь у нас есть внешнее подтверждение, а не только
собственный паритет.

## 4. `.t`, `.vdpack`, `.scene`

* **`.t`**: Port определяет заголовок как `kind=8` → DXT5, 2048×2048,
  8 mip, payload 5 592 320 байт = `4·1024·1024·(1+1/4+…)`. Наш
  `d3tool/texture.py` знает больше кодов (6/7/8 DXT1/3/5 + 16-битные
  форматы + A1R5G5B5) и точное правило mip-цепочки GM (без выравнивания
  субмипов до 4×4). Их вывод не противоречит нашему, но слабее.
* **`.vdpack`**: подтверждённый контейнер — `u32 count`, затем на запись
  `u32 len(name+NUL)`, имя, `u32 size`, `u32 offset`, `u32 flags`, после
  индекса — payload'ы; внутри архива есть непрозрачная запись `index`
  (20 362 байт), которую Port не разобрал и поэтому не умеет добавлять
  новые пути (только same-path замены). **Взято в код:** `d3tool/vdpack.py`
  + `d3tool vdpack list|extract|validate|manifest|pack` (см.
  `docs/FORMATS.md` §6); на распакованной папке `pack → extract` даёт
  побайтово тот же каталог (проверено на `Neutrals/AirElemental` и
  `Empire/Hierophant`, 41 файл / 15.5 МБ).

  **Поправка (раньше здесь стояло «новые пути допустимы»).** Это было
  утверждение, а не факт: единственное runtime-подтверждение в архиве Port
  — *замена payload внутри существующего пака*, а попытка добавить в него
  шесть новых записей при нетронутом `index` в игре не показала юнитов.
  Поэтому теперь `vdpack pack` **предупреждает**, если в паке нет ресурса
  `index`, и умеет `--keep-index <старый.vdpack>` — перенести непрозрачный
  `index` из проверенного пака в новый (та самая «подтверждённая» форма:
  те же пути, другой payload). `vdpack manifest` пишет `index: {bytes,
  sha256}` — по манифесту видно, собран пак на проверенной форме или нет.
* **`.scene`**: Port подтверждает наши же связи — `VDBones`, `bonesuid`,
  `file`/`meshfile` в `.ac`, текстовые ссылки. Нового нет.

## 6. Что ещё взято в код в этом раунде (не из Port, но по ходу сверки)

Сверка `.a`/`.g` заставила перепроверить обратный экспорт на «неудобных»
юнитах, и там нашлись три настоящих дефекта, которые ломали `.g`:

1. **Lightmap-UV блок.** `lmuvdata` — это ровно `vertex_count * 8` байт, и
   читатель берёт длину из числа вершин. Донор отдаёт блок под *исходное*
   число вершин, а Blender-пересохранение делит вершины по швам
   (Hierophant: 3397 → 3406). Записанный «донорский» блок сдвигал всю
   таблицу костей и следующий меш — файл переставал разбираться.
   Теперь блок всегда ровно `vc*8` (`gfile._fit_lm`), а при пересборке
   предпочитается lane из glTF, если он совпадает по длине
   (`gltf._pick_lm`).
2. **Объявленное число влияний.** Донор может объявлять
   `weights_on_vertex=3`, а пересобранная сетка иметь одну кость; и
   наоборот, `w=1` при нескольких костях означает *двухвлиятельную* запись.
   Теперь ширина записи считается как `_eff_width`, а объявленное значение
   правится только если из него выводится другая ширина
   (`gfile.write_geometry_file`, `_part_block`).
3. **Несвязанные меши юнита.** Morph-основа (плащ Hierophant) и жёсткие
   части не имеют armature-модификатора, поэтому не попадали ни в выборку
   glTF, ни в сборку — и слоты донора разъезжались (5 частей → 4, часть
   головы уезжала в trailing). Импорт теперь метит **все** созданные меши
   (`d3unit_part` + `d3unit_owner`), а экспорт собирает меши своего юнита
   по владельцу, не задевая соседний юнит в сцене
   (`importer._tag`-вызов, `exporter._collect_unit`).

Аддон: **19/19** сценариев (`tests/blender_addon_test.py`), включая
`extra rigid mesh follows its bone`, `extra mesh can share the body atlas`,
`rigid unit round trip`, `morph unit round trip`,
`other units in the scene keep out of the export`.
Ядро: `test_d3tool` 74/74, `test_corpus` 16/16, `corpus_parity` 84/84 EXACT,
`reverse_parity` 84/84 EXACT, `anim_audit` 0 проблем.

## 7. Где Port ошибался (и почему это важно)

* Первая модель `.a` (36-байтный заголовок + 16-байтные quaternion-префиксы
  + сдвиг позиций на кадр) — **неверна**; они сами её отозвали после
  дизассемблирования `geo2011.dle`. Все их runtime-пакеты до этой правки
  использовали структурно некорректный `.a`.
* «16-байтные префиксы у каждой кости кроме последней» — артефакт того же
  заблуждения: при чтении по грамматике `<3If` эти байты оказываются
  началом следующей записи либо кадрами предыдущей.
* Их `d3g_container.py` принимает `influences ∈ {0,1,3,4}` и **отказывает**
  на `w=2`; в игровом корпусе двухвлиятельная запись встречается
  (паук, броня) — наша реализация её поддерживает.
* Tangent-поток они тоже не разбирают (в их парсере это `tail`), но он у
  них хотя бы описан — за это и взяли.

## 8. Что можно взять дальше

1. ~~**`.vdpack` reader/writer**~~ — **сделано** в этом раунде:
   `d3tool/vdpack.py`, команды `vdpack list` / `extract` / `pack`, 5 тестов
   в `tests/test_d3tool.py` (раскладка байт, реальная папка юнита, битые
   архивы, защита от `..`, CLI-цикл). Осталось необязательное: команда
   `vdpack validate`, которая проверяет, что все `.ac`/`.scene`-ссылки
   внутри архива разрешаются (у Port это `validate_tree`).
2. **`.a2`** — Port сознательно не поддерживает; в корпусе `.a2` нет, так что
   до появления файла делать нечего.
3. **PSA/PSK-путь** (`psa_to_d3a.py`) — полезен только для переноса H7-клипов;
   к нашей задаче (D3 ⇄ Blender) отношения не имеет. Знание, которое стоит
   сохранить: перестановка `(x,y,z,w) → (x,z,y,w)`, сдвиг позиций
   `D3[n+1] = 0.0075 · PSA[n].xzy`, `Bip01` и `*-Prop*` — исключения.
4. **`.t` из H7** — кодирование DXT5 2048² с 8 mip; наш `png_to_t` уже умеет
   DXT5, осталось бы только сопоставление material slots (C = ColorMask,
   D = DiffMap) — актуально лишь для модов.

## 8b. Второй проход по архиву (что добрано позже)

1. ~~`vdpack validate`~~ — **сделано**: `reference_findings()` разбирает
   `.ac`, `.scene` и `.g` (материалы → `.t`, дубли имён частей), а не только
   текстовые ссылки, как `validate_tree` у Port. Их исключение «внешняя
   ссылка» сохранено как *note*, а не ошибка.
2. **`manifest`** — **сделано** в этом раунде по образцу их `d3model.py
   manifest` / `manifest.json` рядом с каждым паком: `vdpack manifest
   <folder|archive>` печатает `{path, bytes, sha256}` на файл плюс отчёт о
   ссылках. Документ для папки и для собранного из неё архива совпадает
   побайтово (сортировка без учёта регистра, имена в форме архива), тесты —
   `test_vdpack_manifest_of_folder_and_archive_match` и
   `test_vdpack_manifest_cli_writes_json`.
3. **`.char` — не сделано, и без образца сделать нельзя.** В `NewUnit.vdpack`
   их 21; Port пишет «профили и статистика юнитов» и что правка строки-ID
   внутри payload даёт отдельную строку в Character Browser (runtime
   подтверждён). В нашем корпусе `.char` нет вообще, поэтому мы только
   переносим их как обычный payload и считаем unit-local ссылкой; формата не
   знаем. Нужен хотя бы один файл (например `neutrals_blackbear.char`), чтобы
   описать его так же, как `.g`/`.a`.
4. **Непрозрачная запись `index`** (20 362 байта) внутри архива: у нас она —
   обычный файл, `extract → pack` переносит её дословно, но архив, собранный
   из папки без неё, игры не проверялся. Это записано в `docs/FORMATS.md` §6
   как предупреждение, а не как гарантия.

Что Port оставил открытым, а наш корпус закрывает (полезно, если сверка
пойдёт в обратную сторону):

| открытый вопрос Port | ответ у нас |
|---|---|
| «неизвестно назначение opaque header/service полей» `.g` | прелюдия разобрана, `_prelude_block` + `docs/FORMATS.md` §2 |
| «BlackBear tail / N=2 неизвестны» | запись `w=2` (46 байт) встречается в корпусе (паук, броня) — `_eff_width` |
| «local-матрицы Priestess ошибочны» | bind-матрица `.g` = glTF IBM, читается column-major, 84/84 `reverse_parity` EXACT |
| «multi-material parts» (в их отчётах нет) | диапазоны одного index-буфера; сумма объявляется, разница уходит в `material0` |
| «`.t` mip-цепочка» | правило GM (без выравнивания субмипов до 4×4) + все коды 6/7/8/16/A1R5G5B5 |

## 8c. Перекрёстная проверка парсеров (кто прав, мы или Port)

Прямая проверка «наши чтения против их чтений» на нашем корпусе (их код —
`_work_blender/geo2011_a.py` и `d3g_container.py`, тот, что дал работающие в
игре пакеты):

| файлы | вердикт |
|---|---|
| `.a`, 153 файла | на **62** файлах, которые принимают оба парсера, **0 расхождений** (число треков, кадров, fps); ещё **91** файл их парсер отвергает (`invalid animation header`), а наш читает — это многопоточные `_baseanims.a`/`_iadd.a`/`*_run.a`, где в одном файле лежит несколько потоков подряд и заголовок покрывает только первый |
| `.g`, 160 файлов | их парсер принимает 60; на **58** из них суммы (вершины, треугольники, кости) совпадают до числа; 2 расхождения — `Leader-Ranger`/`Leader-Thief`, те самые node-хелперы (`materials_num 0`, 4 вершины, объявлено 2 треугольника, но индексного потока нет): они верят объявленному полю, мы — фактическим индексам |
| остальные `.g` | их парсер отвергает 66 файлов по `weights_on_vertex` (код влияний 2 — они его правильно считают, но не принимают), 20 по `unverified influence layout: 2`, 6 по «rigid layout requires exactly one bone», плюс единичные `invalid string`/`unconsumed tail` на составных файлах |

Что это меняет по существу:

1. **`.a` — мы не расходимся, мы шире.** Формула их же `geo2011_a.py`
   (`<5I` заголовок, `<3If` запись, `<7f` кадр) — это ровно наша; и
   **тот самый пакет, который у пользователя заработал (Blade Dancer),
   собран именно этим модулем** (`build_bladedancer_test.py` импортирует
   `geo2011_a`). Исторический 36-байтовый вариант (`d3a_container.py`) сам
   помечен как опровергнутый — в наших `.a` он и не применяется.
2. **`.ac` — 1-based версия не подтверждена.** В `build_priestess_animation.py`
   диапазоны пишутся как `start+1 … end+1` (1-based), а в
   `build_bladedancer_test.py` — `start … end` (0-based inclusive). Работает
   в игре именно второй, и он же совпадает с корпусом (см. `FORMATS.md` §3:
   `frame0 0` в 23 состояниях, `frame1 == frames` не встречается ни разу).
   Отсюда правка: наш **генератор** `.ac` писал `frame0 1 / frame1 <count>`
   (на кадр мимо с обеих сторон) — теперь `0 … count-1`, а проверка
   готовности к бою ловит `frame1 >= count`.
3. **`.vdpack` — здесь мы утверждали лишнее**, см. поправку в §4: единственный
   подтверждённый игрой сценарий — замена payload в существующем паке, поэтому
   `--keep-index` и предупреждение вместо обещания «новые пути допустимы».
