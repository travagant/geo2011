# Почему локальная модель считает процессором и как это проверить

Короткий ответ: **карта тут ни при чём, решает Ollama в момент загрузки модели.** Она сама кладёт
в видеопамять столько слоёв, сколько, по её расчёту, влезает *в этот момент*, а остальное держит
в оперативной памяти. Если влезло не всё, каждый токен идёт по шине PCIe — карта при этом может
показывать «свободно», а ответы будут в разы медленнее. Смотреть надо не в диспетчер задач, а в
цифры, которые отдаёт сам Ollama: `size` (весь вес модели) и `size_vram` (сколько лежит в VRAM).

## Три состояния

| `size_vram` | Что происходит | Скорость |
|---|---|---|
| равен `size` | все слои на карте | нормальная |
| между 0 и `size` | часть на карте, часть в RAM | самая медленная: каждый токен через PCIe |
| 0 | всё на процессоре | медленно, но ровно |

## Причины по порядку вероятности

1. **Переменная окружения запрещает карту.** `OLLAMA_NUM_GPU=0`, `CUDA_VISIBLE_DEVICES` пустой,
   `-1` или указывает на несуществующий номер, `OLLAMA_LLM_LIBRARY=cpu*`, `OLLAMA_NO_CUDA=1`.
   Ставятся обычно из чужого `start.bat`/инструкции «если не хватает памяти» и остаются жить.
   Проверка: `Get-ChildItem Env: | Where-Object Name -match 'OLLAMA|CUDA|HIP|NVIDIA'`.
2. **В момент загрузки карта была занята.** Студия (ComfyUI на 8190/8191), SDXL, браузер, чужой
   ComfyUI на 8188. Ollama увидела мало свободной памяти и ужала модель. Отсюда «то быстро, то
   медленно»: всё зависит от того, кто держал карту в момент загрузки.
3. **Модель стала больше.** Другой квант (Q8 вместо Q4), 9B вместо 8B, плюс контекст `num_ctx 8192`:
   веса и кеш контекста складываются, и в 8–11 ГБ помещается уже не всё.
4. **Ollama обновилась.** Новая сборка могла прийти без CUDA-библиотеки или перестать видеть
   старую карту. В `%LOCALAPPDATA%\Ollama\server.log` будет либо `library=cuda`, либо `library=cpu`
   и `no compatible GPUs`.
5. **Драйвер.** После обновления драйвера/переустановки Windows Ollama иногда видит карту, но не
   получает память. Проверяется строкой `inference compute` в том же логе.
6. **Модель выгружается между сообщениями.** Тогда каждое сообщение начинается с загрузки файла с
   диска — это выглядит как «считает процессором», хотя считается на карте. Лечится `keep_alive`.

## Проверка в нашей студии

```powershell
# что сейчас загружено и где считается
curl.exe -s http://127.0.0.1:3210/api/llm/gpu
```

Ответ: `verdict` = `gpu` / `partial` / `cpu` / `idle` / `offline`, `loaded.sizeVram` и `advice` —
готовая фраза с числами. То же самое короткой строкой видно в «Подключения» → локальная LLM:
«В видеопамяти: 6.1 GB весов на карте» / «В видеопамяти только 55% весов…» / «Считает процессор…».

Глазами Ollama:

```powershell
ollama ps          # колонка PROCESSOR: 100% GPU / 55%/45% CPU/GPU / 100% CPU
curl.exe -s http://127.0.0.1:11434/api/ps
Select-String -Path "$env:LOCALAPPDATA\Ollama\server.log" -Pattern 'library=|inference compute|no compatible'
```

Важно: сразу после ответа с `keep_alive: 0` модель уже выгружена, и `ollama ps` пуст — это не
признак процессора, это признак выгрузки (состояние `idle`).

## Что студия делает сама

| Место | Поведение |
|---|---|
| `server/llm-gpu.mjs` | спрашивает `/api/ps`, считает `size_vram / size`, выдаёт вердикт и подсказку |
| `server/llm.mjs` | `keep_alive` больше не `0`: по умолчанию модель живёт **5 минут** после ответа, поэтому второе сообщение отвечает сразу |
| `POST /api/jobs` | перед 3D-генерацией студия освобождает VRAM ассистента (только если модель действительно загружена) |
| `POST /api/llm/unload` | та же выгрузка по кнопке «Освободить видеопамять» |
| `GET /api/llm/gpu` | диагностика: онлайн, версия, что загружено, вердикт, совет |
| `GET /api/status` | в `ollama.gpu` та же сводка для интерфейса |

Новых полей в настройках нет — по вашему требованию; всё настраивается переменными окружения:

| Переменная | Смысл | По умолчанию |
|---|---|---|
| `ASTRA_LLM_KEEP_ALIVE` | сколько держать модель после ответа: секунды, `5m`, `-1` (вечно), `0` (старое поведение) | `5m` |
| `ASTRA_LLM_NUM_GPU` | сколько слоёв класть в VRAM: `999` = все, `0` = заставить процессор (для проверки) | не задано, решает Ollama |

## Что делать по вердикту

* **`cpu`** — сначала снять переменные из пункта 1, перезапустить `ollama serve`. Если лог пишет
  `library=cpu` — переустановить Ollama (она сама подтянет CUDA) и обновить драйвер. Если в логе
  `library=cuda`, а `size_vram` всё равно 0 — задать `ASTRA_LLM_NUM_GPU=999` и посмотреть, что
  ответит Ollama (она честно скажет, сколько слоёв смогла положить).
* **`partial`** — освободить карту: закрыть ComfyUI/студийные движки или взять модель поменьше
  (`qwen3:4b`). Считайте бюджет: веса + кеш контекста `num_ctx` должны влезать вместе с тем, что уже
  занимает карту.
* **`gpu`**, но медленно — дело не в процессоре: смотреть `load_duration` (загрузка с диска) и
  `eval_count / eval_duration` (токены в секунду). Если загрузка каждый раз с нуля — `keep_alive`
  выставлен в `0` где-то ещё (свой скрипт, старый патч).

## Откат

Правки только в коде студии и двух переменных окружения. Вернуть старое поведение (выгрузка после
каждого ответа): `setx ASTRA_LLM_KEEP_ALIVE 0` и перезапуск студии. Убрать диагностику — откатить
`server/llm-gpu.mjs`, строку `import` в `server/llm.mjs`/`server/index.mjs` и маршруты `/api/llm/*`.

имён с `:latest`, вердикты `gpu`/`partial`/`cpu`/`idle`/`offline`, текст советов с числами, выгрузка
только загруженной модели (`keep_alive: 0` в теле запроса), отказ Ollama не бросает исключение,
