# Исследование моддинга Disciples III для D3Unit

Дата: 20 ноября 2026. Цель — отдельные новые юниты Rebirth с моделями, скелетами, анимациями и текстурами; не подмена донора. Это обзор найденных доступных материалов, а не утверждение, что исследованы все существующие источники. Разные издания и версии игры могут отличаться.

**Статус доказательств:** «код» — прочитана реализация, но внешняя программа не запускалась (в среде отсутствуют Java и Maven); «сообщество» — сведения руководств и форумов, не подтверждённые нашим запуском игры; «наш опыт» — подтверждения и тесты нашего проекта, не распространяющиеся автоматически на другие случаи.

## Главный вывод

[Dis3-modding-automation](https://github.com/DarrMirr/dis3-modding-automation/tree/95f0bdbf454ddb1df11668c15018a36b6c3aa2df) полезен для массового баланса и некоторых операций со сценами. Это **не экспортёр новых моделей и скелетов и не генератор игрового юнита**. Интегрировать Java-инструмент как обязательную зависимость аддона сейчас нет смысла; его идеи и тесты стоит учитывать при создании собственных безопасных проверок и инструментов профилей. Новую функциональность из него мы в аддон не переносили.

## 1. Dis3-modding-automation: анализ исходников

Автор DarrMirr, рассмотрен commit `95f0bdbf454ddb1df11668c15018a36b6c3aa2df`; [релиз 1.0.1](https://github.com/DarrMirr/dis3-modding-automation/releases/tag/v1.0.1) содержит JAR, README проекта указывает Java 21. Maven и Apache POI используются при сборке/работе с таблицами. Проект содержит тесты, но они здесь не запускались. Репозиторий указывает лицензию CC BY 4.0: перед копированием кода или распространением следует отдельно проверить условия атрибуции, совместимость с лицензией нашего проекта и лицензии зависимостей. Простая ссылка на источник не означает, что эти вопросы решены.

| Команда | Что обнаружено в коде | Применение и ограничения |
|---|---|---|
| `character_stats_to_xls` | Читает `.char` и заполняет XLSX по встроенному шаблону. | Для массового сравнения и баланса, не для полного клонирования профиля. Имя персонажа должно совпасть со строкой шаблона; для отсутствующего ID строка автоматически не создаётся. |
| `xls_to_character_stats` | Читает таблицу, вычисляет формулы и генерирует `*_stats.char` в `output`. | Результат пересоздаётся по ограниченному списку полей; требуется посимвольная/семантическая проверка, см. ниже. |
| `collect_model_files_into_dir` | Рекурсивно **копирует** только `.g` и `.a` в одну уже существующую папку. | Не собирает `.scene`, `.ac` или текстуры; одинаковые имена конфликтуют, структуры исходных папок не сохраняются. Не анализирует связи между файлами. |
| `accommodate_model_files_from_dir` | Рекурсивно **перемещает** `.g`, `.a`, `.t` в подпапки, выбираемые эвристически по имени. | Операция изменяет исходную папку; предназначена для известных соглашений имён и не гарантирует восстановление исходной иерархии. Использовать только на копии. |
| `print_area_zones` | Печать зон арены из конфигурации. | Для работы с аренами, не с юнитовым скелетом. |
| `copy_unit_arena_location` | Копирует локаторы арены и удаляет параметр `resourcefile`, выводит сцены в `output`. | Полезно для арен; не применять к юнитовым сценам без проверки. |
| `fix_pass_point_name_scene` | Исправляет имена точек арены, сохраняет в `output`. | Для hexmap/арен. |
| `insert_child_scene_block` | Вставляет блоки сцены к родителю с указанным именем, записывает `output`. | Идея полезна для модификации сцен, но нужен отдельный тест на наших файлах. |

`DeleteSceneBlockCommand` существует как пустой класс, в `CommandFactory` не зарегистрирован: считать его рабочей командой нельзя. Парсер аргументов ищет аргументы, начинающиеся с имени: актуальные примеры из [руководства по Excel](https://steamcommunity.com/sharedfiles/filedetails/?id=3730952730) используют `command=... source="..."`, без ведущего дефиса; в старом руководстве по масштабу показаны аргументы с дефисами, что не соответствует прочитанному парсеру. Проверяйте README и версию.

### Важные риски Excel-обмена — вывод из кода

- Это не lossless round-trip: `CharacterStats.toFileContent()` выводит фиксированные группы полей, переформатирует файл, не сохраняет исходные комментарии и произвольные поля. Значения читаются упрощённым разбором строк. Даже известные `no_retreat`, `no_rotate`, `keycharacter` присутствуют в списке колонок, но **отсутствуют в группах записи**. Локальная проверка входного корпуса `Profiles/stats` нашла соответственно 26, 21 и 14 файлов с этими ключами. Это статический вывод о потенциальной потере при обратном экспорте, не эксперимент с JAR.
- Импорт привязан к существующим ID строк шаблона; файлы с неизвестными именами могут быть пропущены без создания новой строки. Обратный экспорт пишет строки таблицы, а не только изменённый юнит. Выходные файлы могут перезаписываться в `output`.
- Автор читает UTF-8 и при ошибке декодирования пробует Windows-1251; файл статистики записывает `Files.writeString` (UTF-8 по умолчанию в этом API). Для команд сцен запись Windows-1251. Это не гарантия сохранения исходной кодировки и форматирования.
- Безопасная процедура: отдельная копия, один знакомый файл, сравнение ключей и значений до/после, обзор удалений, затем отдельный игровой тест. Не заменять автоматически весь каталог игры.

Парсер сцен `BlockParser` строит дерево по строкам, начинающимся с `{`/`}`, и обрезает пробелы и пустые строки. Это не доказательство корректного разбора любого синтаксиса `.scene`. Для нашего аддона предпочтительны сохранение неизвестного содержимого и минимальные изменения, а не безусловная перезапись через этот парсер.

## 2. Форматы и инструменты

[Введение в модели](https://steamcommunity.com/sharedfiles/filedetails/?id=3658787497) и [репозиторий Dis3tool](https://github.com/rootext/dis3tool-release) описывают:

- `.scene` — текстовая сцена: размещение и ссылки на геометрию, материалы и т. п.; стартовая точка набора ресурсов.
- `.g` — бинарная геометрия с дополнительными параметрами; в нашем корпусе встречается skinning и inverse-bind матрицы. Не считать всякий `.g` одинаковым.
- `.a` — анимационные данные; `.ac` — текстовая конфигурация анимаций и событий. Для корректного поведения нужны ссылки и события, не только геометрия.
- `.t` — текстура с собственным 59-байтовым заголовком и данными известных форматов, в том числе DXT; [руководство](https://steamcommunity.com/sharedfiles/filedetails/?id=3674054915) описывает `.t` → DDS через Dis3tool или TGA через Toolkit. Наши детали и ограничения см. `docs/FORMATS.md`.
- Лидеры часто собираются из набора частей и экипировки; простой путь для обычного юнита нельзя автоматически считать достаточным для лидеров.

[Dis3tool rootext](https://github.com/rootext/dis3tool-release) — **отдельная** утилита, не Dis3-modding-automation и не наш пакет `d3tool`. Автор заявляет преобразование `.g`, `.scene`, `.camera` ↔ glTF, `.t` ↔ DDS, распаковку и масштабирование. Степень поддержки обратного пути для каждого типа и конкретных анимаций требуется проверять. В [руководстве по геометрии](https://steamcommunity.com/sharedfiles/filedetails/?id=3664471027) автор рекомендует поместить связанные `.g`, `.a`, `.t` рядом со `.scene` перед её декодированием; в комментарии он предлагает glTF → `.g`, импорт `.g` в сцену Toolkit и при необходимости замену шейдеров на шейдеры похожего оригинального объекта. Это предложение сообщества, не доказательство полного экспорта собственного скелета и работоспособного юнита.

[Масштабирование](https://steamcommunity.com/sharedfiles/filedetails/?id=3661189621): автор советует изменять `.g` и соответствующие `.a` одинаково, а FX и их позиции проверять отдельно; Dis3tool перезаписывает файлы. Работать только с резервной копией. [Треки камеры](https://steamcommunity.com/sharedfiles/filedetails/?id=3669603720): `.camera` можно изучать через Dis3tool/glTF; это второстепенно для текущей задачи.

Наши конвертеры и аддон уже решают другую часть задачи: экспорт геометрии и анимации с учётом известных форматов, а также диффузной текстуры. Арбитр с автоматически экспортированной diffuse был показан пользователем в игре на существующем юните. Это **не** подтверждает независимую регистрацию нового юнита или произвольные скелеты. Подробности и ограничения — `README.md`, `docs/FORMATS.md`, `docs/NEW_UNIT_REBIRTH_RU.md`.

## 3. Ресурсы, архивы, локализация

[Структура ресурсов](https://steamcommunity.com/sharedfiles/filedetails/?id=3650128256): `resources/Characters` — модели/анимации/текстуры, `resources/Profiles` — профили, статы и навыки, `resources/Languages` — локализация, `resources/FX` — эффекты, `resources/Hexagons` — арены, `system` — в том числе интерфейс и графические настройки. Описания некоторых разделов `system` сам автор считает предположениями.

[Распаковка](https://steamcommunity.com/sharedfiles/filedetails/?id=3651840590): Toolkit → Tools → Export mod либо Dis3tool; [рекомендации автора](https://steamcommunity.com/sharedfiles/filedetails/?id=3656717573) — извлекать базовые архивы и патчи последовательно, держать оригиналы отдельно от рабочей папки и класть в мод только изменённые файлы. При перекрытиях важно проверить фактический приоритет нужной сборки, а не считать порядок по имени универсальным. На компьютере пользователя есть именно `russian.vdpack`, а не `ruru.vdpack`; наличие примерно 2 ГБ не означает, что его надо копировать целиком в каждый мод.

[Общее руководство](https://steamcommunity.com/sharedfiles/filedetails/?id=3647174097) описывает замену ресурса тем же путём внутри мод-пакета, создание через Toolkit Create Mod, размещение пакета в `Documents/My Games/Disciples Reincarnation/Mods` и включение в настройках дополнений. Папка `system` в некоторых модах устанавливается отдельно в каталог игры: это может конфликтовать с другими изменениями, нужны backup и отдельные инструкции. Утверждения о единственном способе упаковки и об ограничениях количества модов в руководстве — опыт автора, не универсальная гарантия. Наш `d3tool vdpack pack ... --reindex` создаёт архив с manifest, но новый юнит из него **ещё не подтверждён в игре**. Прежний архив с новыми файлами без обновления manifest дал `Unindexed file`.

[Локализация](https://steamcommunity.com/sharedfiles/filedetails/?id=3643857095): автор описывает `resources/languages/{language}/texts` и параметр `sLanguage` в `user.ini`; предупреждает, что при смене каталога языка оригинальные переводы могут перестать находиться и потребоваться их перенос. Проверять на конкретной установке; не менять язык пользователя автоматически и учитывать права на распространение игровых ресурсов.

## 4. Создание нового юнита: что известно и чего нет

[Обсуждение Modding Q&A](https://steamcommunity.com/app/10270/discussions/2/558747922795146582/) и [продолжение](https://steamcommunity.com/app/10270/discussions/2/558747922795146582/?l=russian&ctp=2) дают примеры изменения ID и профилей, `skill_grid`, локализованных строк, таблиц `unit_<faction>` и `town_<faction>`, упаковки. Конкретные таблицы, пути, формат, регистрация в редакторе, найм и ветка улучшений зависят от цели и версии: это карта для исследования, а не готовый рецепт. В [Tribute](https://steamcommunity.com/app/10270/discussions/2/558747922795339423/?ctp=3) отдельно упоминаются изменения `system` для дерева улучшений в этом моде и старый путь через 3ds Max с плагинами; оба утверждения требуют воспроизведения.

Наш `create_profile_project` в версии 1.1.57 создаёт отдельный staging: новый корневой `.char` и копии непосредственно подключённых `desc/stats/sound`. Модель, иконки, локализация, способности и вложенные include ещё могут ссылаться на донора. Регистрация, наём, упаковка мода и независимая модель не реализованы и не тестировались в игре.

### Предлагаемая последовательность работ

1. Взять проверенный донорский профиль и **без изменения модели** создать новый ID; составить отчёт по всем ссылкам, рекурсивным include и отсутствующим файлам. Сопоставить записи регистрации и локализации с реально распакованной версией пользователя.
2. На копиях подготовить минимальный мод, явно показать добавленные/изменённые файлы и конфликты, упаковать с корректным manifest; проверить включение, наличие юнита и найм в игре, сохранив оригинального донора. Если этого недостаточно — диагностировать регистрацию/путь/логи, не выдавая догадку за причину.
3. Создать отдельные ресурсы модели и текстуры и переключить ссылки нового профиля; проверить как появление, так и бой. Сначала оставить совместимый скелет донора — это отдельный этап, не конечное решение.
4. Затем минимальный новый скелет и анимация: проверить иерархию и имена костей, веса и допустимые влияния, матрицы bind/rest, согласованность `.g`/`.a`/`.ac`, события и переходы. Тесты: импорт обратно, сравнение ключевых поз, открытие в Toolkit, игра: idle, ходьба, атака, получение урона, смерть и повторная загрузка. Отдельно оценить отсутствие/замену событий и FX.
5. Для Heroes V сначала доказать извлечение конкретного образца меша **вместе** со скелетом, весами и анимациями; затем преобразование в Blender и наш экспорт. [modkit-extensions-nival](https://github.com/hometlt/modkit-extensions-nival) и [homm5-editor](https://github.com/senyaak/homm5-editor) — потенциальные источники для `.xdb`, Granny GR2 и ресурсов; рабочая цепочка в Blender и право распространения контента не проверены. Качество привязки делает пользователь; наша задача — корректно переносить и проверять данные, которые ожидает игра.

LOD, как договорились, отложены; пока нужно лишь не делать вид, что разные LOD автоматически используют совместимую UV и текстуру. Проверка новых текстур в loose index в 1.1.56 экспериментальная, в игре не подтверждена.

## 5. Остальные источники и пробелы

- [Официальный репозиторий Dis3tool](https://github.com/rootext/dis3tool-release) — список функций и публичное описание контейнеров и `.t`; это ориентир, а не гарантия поддержки всех вариантов.
- [Руководство по картам/модам Rebirth](https://www.playground.ru/disciples_3_reincarnation/guide/disciples_rebirth_instruktsii_po_sozdaniyu_kart_i_modov_dlya_disciples_pererozhdenie-1205245) — архивы, патчи, упаковка.
- [Обсуждение старого Toolkit и `.vdpatch`](https://steamcommunity.com/app/10270/discussions/2/1621726179563034708/) рекомендует переименовывать копию расширения; это совет для конкретной проблемы старой версии, не менять оригинальные архивы.
- [Habr: El Clasico](https://habr.com/ru/articles/929464/) — авторский контекст проекта; изучен не весь многостраничный материал, его результаты здесь не считаются технической проверкой.
- [XNALara-io-Tools](https://github.com/Valerie-Bosco/XNALara-io-Tools): импорт XPS Арбитра уже проверен в нашем окружении Blender 4.2. Это не устанавливает универсальную совместимость всех XPS.
- [ModDB Retribution](https://www.moddb.com/mods/retribution) предупреждает о несовместимости модов разных редакций; нельзя переносить готовые рецепты между Renaissance и Reincarnation без проверки.

**Открытые вопросы:** точный полный набор регистрации и найма в установке пользователя; корректная упаковка именно добавленных ресурсов; независимые пути и модели; экспорт нового скелета и анимационных событий; поведение шейдеров/FX и материалов; извлечение полноценных анимаций Heroes V. Новых игровых испытаний в ходе этого исследования не проводилось. Не все интернет-архивы и старые форумы доступны, и исследование не исчерпывает все материалы сообщества.
