# Промт для battle-арены Coarena — набор 2 (непохожие задачи)

Первый набор состоял из трёх задач одного вида («вот симптом, вот строка, почините»), и сторожа арены приняли его за шаблон. Этот набор намеренно разный по типу работы: **ресёрч**, **инструмент**, **дизайн правила**, **отладка по логу**, **формат документа**. Меняется и форма ответа, так что копия шаблона не читается как копия.

## ПРОМТ A — расследование (ответ: отчёт + диаграмма)

Ты — инженер по разбору аварий. Репозиторий https://github.com/travagant/geo2011 (Python 3, только stdlib). Внутри — `d3tool/`, библиотека читает/пишет форматы игры Disciples III (.g/.a/.scene/.ac/.t) и обменивается glTF, плюс тесты в `tests/`.

Вопрос: где в этом конвейере теряется информация при перегоне glTF → GM → glTF, и что именно теряется?

Что сделать:
1. Составь карту пути данных: какие поля glTF где читаются (`d3tool/gltf.py`, `Model`/`load_gltf`), где пишутся в бинарный формат (`d3tool/gfile.py`) и где читаются обратно (`d3tool/gltf_out.py`). Укажи конкретные функции и строки.
2. Найди не менее трёх категорий данных, которые glTF не может выразить, а движок требует (например строки, атрибуты, служебные блоки). Для каждой — что происходит при обратном экспорте и откуда берётся значение (так называемый «донор»).
3. Опиши, что случится, если донора нет вообще (юнит собран с нуля, не из игры).
4. Дай таблицу: категория | при потере — падение/тихая деградация | как проверить.

Формат ответа: текст ≤ 900 слов + одна ASCII-диаграмма потока данных. Не пиши код, кроме коротких фрагментов с номерами строк.

## ПРОМТ B — инструмент (ответ: рабочий скрипт)

Ты — разработчик CLI. Репозиторий https://github.com/travagant/geo2011, Python 3 stdlib. Есть `d3tool gattr <file.g> --part N --insert key=value` — вставляет или заменяет один атрибут в одном блоке одного `.g`.

Напиши отдельный скрипт `tools/gattr_table.py`, который делает то же самое таблицей:
- вход: `--set "part=4;key=new_vertex_weights_format;value=1"` можно повторять сколько угодно раз;
- предварительно печатает таблицу «блок | имя | ключ был | ключ станет», затем спрашивает подтверждение `[y/N]`, если не передан `--yes`;
- пишет результат атомарно (временный файл + os.replace), при любой ошибке исходник не трогает;
- `--dry-run` печатает таблицу и выходит с кодом 0, ничего не записав.

Ограничения: только stdlib; переиспользуй парсер и писатель из `d3tool/gfile.py` (не копируй логику формата); для формата `.g` не делай своих байтовых структур. Покажи полный файл и пример прогона на `Empire/Angel/character_empire_angel.g` (блок 4, ключ `new_vertex_weights_format`).

## ПРОМТ C — дизайн правила (ответ: спецификация)

Ты — проектировщик совместимости. Репозиторий https://github.com/travagant/geo2011. Задача: экспорт одного юнита делает 4–10 файлов, и часть из них — общие для папки (`Aliases/`, `<stem>_lod.g`, `.scene`). Сейчас при экспорте в чужую папку часть файлов перезаписывается, часть добавляется, и пользователь узнаёт об этом уже после.

Спроектируй правило «что считается изменением юнита» и напиши его как спецификацию:
1. классификация каждого файла папки: основной / производный (LOD) / общий на папку / чужой;
2. матрица «действие экспорта × категория файла × есть ли донор» → перезаписать / добавить / предупредить / отказаться;
3. правила именования, чтобы два юнита в одной папке не затирали друг друга;
4. как откатывать частичную запись, если на 7-м файле упало;
5. 6–8 тестовых сценариев, которые надо добавить в `tests/` (название + что проверяет + ожидаемый итог).

Формат: спецификация ≤ 1200 слов, без кода. Если видишь, что текущее поведение уже правильное — так и скажи, но докажи ссылкой на функцию и строку.

## ПРОМТ D — отладка по логу (ответ: диагноз + патч)

Ты — дежурный инженер. Репозиторий https://github.com/travagant/geo2011. Пользователь запускает `d3tool vdpack scan "…\Mods" --strict` и получает отказ игры. Журнал игры короткий:

```
00:07:11  Load unit: resources\characters\empire\knight\character_empire_knight.scene
00:07:11  ERROR: mesh "weapon_empire_knight_sword" not found in archive
00:07:11  Load failed: resources\characters\empire\knight\character_empire_knight.scene
```

Вопрос: какие причины дают ровно такой лог и в каком порядке их проверять? Разбери не менее пяти гипотез (имя файла, регистр букв, путь в манифесте `index`, сам `.g` без части, LOD-подмена, сцена ссылается на старую папку), для каждой — какая команда d3tool её подтверждает или снимает. Затем: что добавить в код, чтобы `vdpack scan` сам печатал причину, а не только имя архива. Дай минимальный патч.

## ПРОМТ E — документ (ответ: markdown-файл)

Ты — техписатель. Репозиторий https://github.com/travagant/geo2011. Внутри есть огромный `README.md` (900+ строк) и `docs/FORMATS.md` с разбором бинарных форматов.

Напиши новый `docs/CHEATSHEET.md` — шпаргалку на одну страницу для моддера, который впервые открыл репозиторий:
- 8 самых частых задач («заменить текстуру оружия», «добавить меч юниту», «перекрасить броню», «поправить анимацию», «собрать мод-архив»…) → команда + 1–2 строки пояснения;
- блок «не работает — проверь сначала это» из 5 пунктов;
- таблица «файл формата → чем читать/писать»;
- ни одного выдуманного ключа: только то, что реально есть в `d3tool/cli.py` (проверь аргументы).

Формат: только markdown, ≤ 1500 слов, без кода на Python.
